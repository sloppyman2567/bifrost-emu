FrostJIT: how bifrost-emu runs ARM64 code on an x86_64 PC

A phone game is machine code for ARM64 processors, which a PC's x86_64 processor cannot run. FrostJIT, bifrost-emu's just-in-time compiler, translates that code into native x86_64 code while the game runs, keeps the translation and reuses it. Your PC then runs mostly its own code, instead of interpreting the game one ARM instruction at a time.

From ARM64 to x86_64

The first time a piece of code runs, it goes through these steps once. After that, the translated code runs directly.

  1. ARM64 codeThe game's own machine code, read from its files.
  2. DecodeEach instruction is read by the decoder the interpreter also uses.
  3. IR and SSAA typed intermediate form where values are tracked and simplified.
  4. x86_64 codeRegisters are assigned and native PC instructions written.
  5. Chained blocksTranslated blocks jump straight to each other.

An interpreter runs anything the JIT does not translate, and it is the reference the JIT is checked against. The JIT guide maps each step to its source.

What makes it fast

Translated once, run many times

Code is compiled in blocks of up to 32 instructions (a loop body up to 64) the first time it runs, and kept in a code cache.

Blocks jump to each other

A translated block jumps straight into the next one. Returns and other computed jumps go through a per-thread lookup table, not back through the emulator.

Values stay in registers

Loop counters and hot values stay in the PC's registers across loop iterations, and ARM condition flags stay in the PC's own flags wherever the next instruction can use them.

Native vector and float math

ARM NEON and floating-point instructions become SSE and AVX instructions. The JIT uses AVX2, FMA3, BMI2 and the other extensions your CPU has, with fallbacks.

One cache for every thread

A game's threads share one JIT. A full code cache (512 MiB by default) is replaced as a whole and the old code freed once no thread can still be running it.

Warm helper processes

Android starts an app's helper processes by forking a prepared process. Each child keeps the parent's translations, so it starts out running native code.

Experimental and off by default: Tier-2 regions, which fuse a hot path of several blocks and keep it only if a timed trial shows it faster, and a disk cache that reuses translations from an earlier launch.

How fast

CoreMark, an integer and control-flow benchmark, measured on $host ($measured): the current build runs $vs_qemu times as many iterations per second as QEMU's user-mode emulator.

Correct first, then fast

Checked against a reference

A verification mode runs each translated block next to the interpreter and compares the results, and many of the tests' expected results were checked under QEMU.

Exact faults

When guest code touches memory it must not, the game's own crash handler sees exactly the state an ARM CPU would show at that instruction. Android's runtime relies on it.

ARM floating-point rules

NaN results, signed zeros and fused multiply-adds follow ARM's rules, not x86's, so math gives the same answers as on a phone.
